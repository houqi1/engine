# Hut 支撑强弱异常：实现核查（2026-09-28）

本次对照当前 Release 库，定位“多柱底座比严重破坏后的上部更容易塌”。
截图没有保存对应几何、接触载荷和物体休眠状态，所以以下区分可复现的实现错误与截图的待确认解释。

**场景澄清：用户确认截图里的上部与底座仍是整体连通物体。第 2 节的多个独立碎块
缓存缺陷不适用于这张截图，不能作为该现象的归因。该节仅记录另行复现的独立缺陷。
下文的数值均为修复前的诊断记录。**

## 1. 已复现：偏心接触力矩进入求解器时符号错误

接触映射 `src/blast/ContactLoads.cpp` 正确计算物理力矩 `tau = (point-center) cross F`。
P3 扩展 `third_party/nvblast/patches/apply_p3_extstress.py:103` 将它作为正的 `tau / inertia`
写入求解器角向输入。当前 SDK 实际 coupling 运算则是
`y0.angular += M - offset0 cross F`，其中 offset 为节点中心到 bond 的位移。
线性、角向输入的组合因此与物理力矩约定不匹配；应在扩展的边界转换角向符号。
不能通过反转 ContactLoads 的物理叉积来修复，否则会破坏其物理合力矩接口。

用当前 Release 库建立四节点悬臂，末节点 x=3 m，检查 x=2.5 m 的 bond。
施加向下 1000 N，只改变该节点上的作用点。全部结果已经收敛，独立残差约 1e-6：

| 作用点 x（m） | 实际力臂（m） | 应有弯矩幅值（N·m） | 当前计算（N·m） |
| --- | --- | --- | --- |
| 2.8 | 0.3 | 300 | 700 |
| 3.0 | 0.5 | 500 | 500 |
| 3.2 | 0.7 | 700 | 300 |

当前相当于将局部偏心距反向计入：本该抵消的弯矩可能相加，本该相加的可能抵消。
柱脚、底座等有多个接触点的位置会受影响，但不能只凭柱子数量判断误差方向。
P5 的弯曲应力与弯矩成正比，会直接放大这个输入错误的后果。
P6 验证的是传入方程的数值残差，不能识别物理载荷符号本身写错。

此前的接触映射检查只验证进入 SDK 前的合力/合力矩；收敛参考场景的支撑力
经过节点中心，没有覆盖这条偏心力矩路径。这解释了为什么既有检查没有暴露此错误。

## 2. 已复现：编辑一个碎块，另一个休眠碎块的支撑载荷消失

`StructureWorld::applyOccupancyRemoval` 重建同 family 的各个 actor 时，保留了归属、
材料、几何和部分 bond warm start，但没有迁移 ActorBinding 的 contactLoads。
`rebuildBindingsFromFamily` 中的缓存移动只用于同实例中的已有 binding，不能补回
已销毁实例的缓存。场景只保证唤醒被编辑物体，未编辑的休眠碎块不会补发接触冲量。

当前 Release 的独立复现：

- 同一 family 中的两个独立碎块都已承受稳定支撑力，随后休眠。
- 只在第一个碎块删除一个 fine。
- 第二个碎块的接触载荷由 **753.4077 N 变为 0 N**。
- 第二个碎块的应力随后为 **0 Pa**，几何与支撑并没有改变。

这种缺陷会让独立的休眠碎块发蓝、看起来异常耐破坏；用户确认的整体连通 hut 不属于此复现场景。
这项错误不是上一次颜色刷新修复的同一问题：颜色现在可以正确刷新，却展示了错误的零载荷结果。
NVIDIA 官方文档也明确说明，动态结构需要支撑反力才能产生相应的承重应力：
https://docs.omniverse.nvidia.com/kit/docs/blast-sdk/latest/docs/api/extensions/ext_stress.html

## 3. 已确认的断裂时序风险：未收敛结果仍可造成永久损伤

`StructureWorld::solveInstance` 在每次 update 后调用 collectPendingFracture。
该函数检查 fractureEnabled 和 overstressed count，但不检查 SolveStatus。
所以 IterationLimit 的中间解也会生成损伤并被应用。

已有真实 hut 的无断裂诊断在挖掘后第 200 tick 才首次通过收敛验证。
启用断裂时，中间应力会提前改变 bond health 和拓扑；提高最终求解精度并没有自动
修复这一时序问题。尚未用截图对应状态证明这是多柱底座过早破坏的主因，不能把它当成
已经量化的解释。修改时需要区分静态承重与瞬时冲击，不能直接无限等待每帧完全收敛。

## 处理顺序

1. 修复物理力矩到 SDK 的符号转换，并覆盖偏心距正负、接触点移动、整体旋转。
2. 重建时按物体归属和稳定节点信息迁移有效支撑载荷，必要时重新映射作用点并唤醒接触体；
   不能直接复用已改变的 graphNode 索引，也不能保留已被删除的接触。
3. 让静态承重断裂只依据经过合适可信度判定的应力，明确动态冲击的独立处理策略。
4. 再比较同样载荷与材料下多柱/削弱后的 hut，记录各柱合力、弯矩、连接面积及收敛状态。

正式物理实现本轮未改。诊断程序已单独编译并运行。
复现源码：`build/hut-neck-analysis/support_probe.cpp`；原始输出：
`build/hut-neck-analysis/support-report.txt`。它复用现有梁和碎块构造，未运行其旧测试入口。

## 后续修复（检查点 2f4858d 之后）

- P7 补丁在 addLoad 的 SDK 边界将物理角向载荷取反；ContactLoads 保持物理叉积约定。
  CMake 在 P6 后自动应用该补丁，兼容已经打过旧补丁的构建目录。
- applyOccupancyRemoval 为未编辑的同 family 物体保存接触载荷；重建后通过稳定节点编号
  找到新的 SDK 索引，并按新节点中心换算物理力矩，且仅向拥有该节点的 actor 恢复载荷。
  涉及被编辑物体的旧接触不迁移，以免保留已删除的支撑；它们由物理接触重新产生。
- 生成及应用应力断裂命令均要求 SolveStatus::Converged；公开的应用入口也检查命令快照是否过期。
  未收敛值仍可用于颜色显示，面板明确提示正在等待收敛。
- 默认的直接冲击伤害仍由独立路径处理。选择“冲击转应力”时也遵守应力收敛门槛；
  短暂冲击按发生 tick 排队，当前冲击载荷保留到求解收敛后才消费，避免新增收敛门槛使
  单帧冲击直接消失。不同 tick 不相加为一个大冲击；同 tick 仍按原来的节点力叠加。
  关闭该模式、重置会话或编辑重建 asset 时丢弃旧冲击队列，避免使用失效的节点索引。
  持续变化的动态载荷仍可能延迟应力断裂。

Release 主程序已重新编译。本轮未新增或运行测试，也未复现用户交互截图中的具体切口。
